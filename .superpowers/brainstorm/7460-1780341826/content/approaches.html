Audit Log + Webhook UI — Architecture Approaches

Which structure fits best for the revenue management system?

A

Minimal — Two flat pages

/audit-log — filter table + inline row expand

/webhooks — list with account filter dropdown + create form inline

Account page — "Webhooks" link → /webhooks?accountId=xxx

Webhook deliveries shown as inline expansion on the webhook row

Pros

  • Fewest files to build
  • Fast to implement

Cons

  • Delivery history cramped inline
  • No dedicated webhook detail
B ⭐ Recommended

Standard — List + detail pages

/audit-log — filter table + inline row expand (changes diff)

/webhooks — list all accounts' webhooks + create button

/webhooks/:id — detail page with config + delivery history table

Account page — new "Webhooks" tab showing scoped list

Pros

  • Delivery history has room to breathe
  • Matches pattern of every other feature
  • Webhook detail URL shareable/linkable

Cons

  • More route files (~5 new files)
C

Contextual — Everything in context

/audit-log — global list + inline expand

No /webhooks top-level — webhooks fully embedded in account detail as a tab

Entity pages (invoice, contract) get their own "Audit Trail" tab using GET /api/audit-log/:entityType/:entityId

Pros

  • Audit trail surfaced where users already work
  • Contextual — no need to filter

Cons

  • Conflicts with user's choice (C) for webhooks having a top-level route
  • Many files across entity pages

I recommend B — it matches the existing pattern (accounts, invoices, contracts all have list + detail pages) and gives delivery history the space it needs.
